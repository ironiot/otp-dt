# ShadowLink: A Low-Fidelity Digital Shadow of TransLink Built with Elixir and OTP
### Summary
Every physical transit entity is mirrored by an isolated, supervised process that may live on any node of a cluster. 

OTP behaviour modules used to implement process lifecycles, synchronous request handling, timeouts, state machines, supervision, and failover within the `DigitalShadow` module. That is, the `DigitalShadow` module reuses the generic functionality offered by OTP behaviour modules, and it only implements domain-specific logic. 

### Background and Motivation
A transit network is a natural fit for the actor model. It consists of many entities, among them buses, routes, stops, and service disruptions, that change state independently and concurrently, interact through events, and appear and disappear throughout the service day. 

On BEAM, each entity can be represented by a lightweight process with its own heap and mailbox, scheduled preemptively across all CPU cores, so thousands of shadows can run side by side without shared mutable state or global stop-the-world garbage collection. 

Process isolation confines a defect triggered by one malformed vehicle record to that vehicle's shadow, supervision trees restore failed shadows automatically, and distributed Erlang lets the processes be spread across several machines with location-transparent messaging. These are the properties a city-scale digital shadow needs, and the project aims to show that on the BEAM they are inherited from the platform rather than engineered by hand.

The project deliberately targets low fidelity. Here, a low-fidelity shadow represents each physical entity by a small, discrete state (position, trip assignment, schedule deviation, and synchronization status) that is sampled at coarse intervals and advanced between samples by simple schedule-based rules, rather than by physics-level or agent-based simulation of traffic, dwell times, or passenger loads. 

Under the widely cited classification of Kritzinger et al. [1], a system in which data flows automatically from the physical object to its digital counterpart, but not back, is a digital shadow rather than a digital shadow in the strict sense. 

Because TransLink's API is read-only, ShadowLink is strictly a digital shadow of the network augmented with an internal predictive model. The final report will position the system within that taxonomy and the vocabulary of ISO/IEC 30173:2023 [2], and a stretch goal adds a what-if sandbox in which hypothetical interventions are applied to forked copies of shadows, closing the loop inside the virtual space without implying any control over the real network.

### Data Sources and Constraints
ShadowLink draws on two families of data. The static GTFS bundle provides routes, stops, trips, stop times, shapes, and service calendars; TransLink publishes a new bundle every week, typically by Friday [3], so the reference data store must be able to reload while the system runs. The real-time layer comes from TransLink's GTFS-RT version 3 endpoints, which deliver trip updates, vehicle positions, and service alerts as Protocol Buffers messages, with every request authenticated by a registered API key [4]. 

TransLink's older Real-Time Transit Information (RTTI) API is no longer available [5], so the project depends only on GTFS and GTFS-RT. Because TransLink describes its Open API as covering the regional bus network and bus service operations [5], the real-time layer of the shadow will be bus-centric, while SkyTrain, West Coast Express, and SeaBus routes from the static bundle will be represented at schedule-only fidelity.

The most consequential constraint is the request quota. TransLink's Open API terms of use cap each API key at 1,000 requests per day [6], and one poll of the two feeds costs two requests. Polling vehicle positions and trip updates once a minute each during a four-hour live window already consumes 480 requests, so coarse temporal resolution is an inherent property of this shadow rather than a shortcut, and several engineering concerns become first-class requirements. 

Exactly one poller may run in the whole cluster at any time, a request-budget governor must enforce the daily cap even across crashes and failovers, and nearly all development and testing must run against a recorded corpus of feed snapshots replayed. The dashboard will also display the attribution notice that TransLink's GTFS terms require [3].

### Objectives
The project has five objectives. The first is to build a working low-fidelity shadow of TransLink's bus network that ingests static and real-time GTFS data within the request quota and exposes the shadow's state through a live dashboard and a query API. 

The second is to demonstrate concurrency by mapping each vehicle, route, stop, and disruption to its own process and measuring how the system behaves as the number of shadows grows. The third is to demonstrate distribution by running the shadow on a three-node cluster with route-partitioned shadows and a cluster-wide singleton ingestion service. 

The fourth is to demonstrate fault tolerance through a deliberately designed supervision hierarchy and a repeatable fault-injection campaign whose recovery times are measured and reported. The fifth is to demonstrate how OTP behaviours, extended by a custom `DigitalShadow` behaviour, abstract the implementation details of shadows.

### System Architecture
ShadowLink is a single OTP application, packaged with `mix release` and deployed as a cluster of three nodes, whose supervision tree contains four subsystems. The reference data subsystem is a `GenServer` that downloads the static GTFS bundle, parses it into ETS tables that every shadow can read concurrently without message passing, and swaps in each week's new bundle without restarting the shadows. The ingestion subsystem fetches the three GTFS-RT feeds concurrently, decodes the Protocol Buffers payloads into normalized observation structs, and publishes each snapshot to the cluster; its data source sits behind a small `FeedSource` behaviour with a live implementation and a replay implementation, so the rest of the system cannot tell recorded data from live data. The shadow runtime hosts the shadow processes, activating each one on demand when its entity first appears in the data and passivating it when the entity leaves service, much like the activation model of virtual actors. The interface subsystem is a Phoenix application that provides a LiveView dashboard, a JSON query API, and Telemetry-based metrics.

The shadows form a shallow hierarchy. A vehicle shadow mirrors one bus, holding its last observed position, current trip, and schedule deviation, together with an estimated position that it advances between observations by interpolating along its trip's stop sequence using predicted arrival times. A route shadow aggregates the vehicles currently serving its route and derives indicators such as vehicles in service, average delay, headway regularity, and bunching. A stop shadow is activated only when someone views or queries a stop, and it derives predicted arrivals from trip updates. A disruption shadow, added late in the project as an extensibility test, mirrors an active service alert and flags the routes and stops it affects. shadows publish their derived state over Phoenix PubSub, so the dashboard, other shadows, and the experiment harness subscribe to changes instead of polling processes.

### Exploiting OTP Behaviours to Avoid Reinventing the Wheel

Much of what a digital shadow platform needs is already solved inside OTP, and the project will make that reuse explicit and measurable. `GenServer` supplies the receive loop, synchronous calls that time out and detect a dead server, asynchronous casts, deferred initialization, and hooks for hot code upgrades, which together cover the request-and-response plumbing every shadow needs. `:gen_statem` supplies explicit state machines with state-enter actions and built-in state and generic timeouts, which removes the manual timer bookkeeping that staleness detection and circuit breaking would otherwise require. `Supervisor`, `DynamicSupervisor`, and `PartitionSupervisor` supply restart policies, restart-intensity limits, ordered start-up and shutdown, and sharding of dynamically started children across partitions. `Registry` supplies process naming and lookup, `Task.Supervisor` supplies bounded concurrent work with timeouts, and the `Application` behaviour, together with OTP's distributed applications, supplies boot ordering, configuration, and node failover. Because every process built on these behaviours follows OTP's conventions for special processes, all shadows also gain runtime introspection through the `:sys` module, Observer, and Phoenix LiveDashboard with no extra implementation effort.

The team will then apply OTP's own design principle one level higher. Every OTP behaviour separates a generic part, the behaviour module, from a specific part, the callback module [7], and ShadowLink's `Digitalshadow` behaviour does the same for shadows. Its generic runtime, implemented once as a `:gen_statem`, owns the lifecycle that every shadow shares: a provisioned state before the first observation, a synchronized state while observations keep arriving, a stale state entered automatically through a state timeout when the physical counterpart goes silent, and a retired state when the counterpart leaves service. The runtime also schedules estimation ticks with generic timeouts, registers the shadow, emits Telemetry events, publishes derived state, and plugs into supervision as a transient child. Each shadow type implements only a handful of callbacks that build its model from reference data, apply an observation, advance the estimate between observations, derive indicators, and answer queries. These callbacks are pure functions over plain data, so domain logic can be unit-tested without starting a single process, while concurrency, timing, and recovery remain the responsibility of the runtime and of OTP beneath it.

The abstraction claim will be demonstrated with evidence rather than asserted. In Week 2 the team will build a baseline vehicle shadow from raw `spawn` and `receive`, and in Week 3 it will rebuild the same shadow as a `Digitalshadow` callback module. The comparison will cover lines of code, test effort, and the capabilities that the baseline either lacks or has to hand-roll, including call timeouts, detection of a dead shadow by its callers, supervision compatibility, staleness timers, and runtime introspection. In Week 6 the team will add the disruption shadow, a new shadow type fed by a different feed, without modifying the generic runtime, and will log the effort required as a measure of how well the abstraction generalizes.

### Utilizing Concurrency

Concurrency is utilized at three levels. Ingestion fetches and decodes the three feeds in parallel under a task supervisor with per-request timeouts, so a slow endpoint never blocks the others. Each snapshot then fans out to every affected shadow at once, and because each shadow is an independent process, the BEAM's schedulers spread hundreds of simultaneous updates across all available cores while per-process garbage collection keeps latency predictable. Finally, every browser session on the dashboard is its own LiveView process subscribed only to the topics it displays. The team will measure the latency from snapshot arrival to published shadow state, update throughput, memory per shadow, and scheduler utilization, and will use accelerated replay with synthetic amplification of the recorded corpus, cloning each vehicle ten and one hundred times, to show how the design scales well beyond the real fleet on a single laptop.

### Utilizing Distribution

The distributed deployment runs three nodes discovered automatically through libcluster, first on one machine under Docker Compose and then on separate machines once that configuration is stable. shadows are partitioned by route, so a route shadow and its vehicle shadows share a node and most shadow-to-shadow messages stay local. The ingestion singleton broadcasts each snapshot to every node, and each node activates and updates only the shadows for the routes it owns; a bus that moves onto a trip on another node's route simply retires on the old node and activates on the new one. When cluster membership changes, the partition map is recomputed and shadows for reassigned routes move the same way at the next snapshot, which requires no state transfer because shadow state is rebuilt from observations. Cross-node lookup will use OTP's `:pg` process groups, with Horde's distributed registry and supervisor evaluated as an alternative if time permits. The singleton poller will rely on OTP's distributed application failover and takeover mechanism, compared against a `:global`-registered singleton should the former prove awkward to configure under Elixir releases, and the request-budget ledger will be replicated across nodes, for example in a small Mnesia table, so that a failover cannot reset the daily count. The team will also analyze, though not fully solve, network partitions, in which both halves of a split cluster may each believe they own the poller.

### Utilizing Fault Tolerance

Fault tolerance begins with an explicit classification of state. shadow state is reconstructible, because the physical network remains the source of truth and the next snapshot rebuilds whatever a crash discarded, so shadows can follow the "let it crash" philosophy with confidence. Other state is authoritative and cannot be recovered from TransLink, including the request-budget ledger, the recorded corpus, and experiment logs, so it must be persisted or replicated. The supervision tree is designed around this distinction. shadows run as transient children so that a normal retirement is never mistaken for a failure. Restart intensities on the dynamic supervisors that host thousands of shadows are set deliberately rather than left at the default of three restarts in five seconds, which a burst of simultaneous shadow crashes would exceed. Reference data tables use an ETS heir so that a crash of their owner cannot cascade into mass shadow failures. A `:gen_statem` circuit breaker shields the API client, so an outage moves shadows into the stale state while the dashboard keeps serving last-known values clearly flagged as stale.

The design will be validated by a chaos module that kills random shadows, crashes the poller, terminates whole partitions of shadow supervisors, injects malformed payloads through the replay source, simulates API outages, and stops entire nodes. For each fault the team will measure time to restart, time to resynchronize with the physical network, blast radius in affected shadows, and whether the fault escalated beyond its intended subtree. Results will be reported for a single node in Week 4 and extended to node failures in Week 5.

### Evaluation Plan

The final evaluation covers five dimensions, each tied to an objective. Fidelity is measured as the distance between a vehicle shadow's estimated position and its next observed position, together with the fraction of time shadows spend stale; because the corpus is recorded at 30-second sampling, subsampling it lets the team compare 30-, 60-, and 120-second polling without spending live quota, which quantifies the trade-off between the request budget and shadow accuracy. Concurrency is measured through latency, throughput, memory, and scheduler utilization under increasing synthetic load. Fault tolerance and distribution are measured through the chaos and node-failure experiments described above. The abstraction claim is measured through the baseline comparison and the extensibility test. Every experiment will be scripted against the replay corpus so that an outside reader can reproduce the results.

### Scope

The minimum viable outcome is a three-node cluster that ingests live and recorded GTFS-RT data within the quota, runs vehicle, route, and disruption shadows on the `Digitalshadow` runtime, survives the chaos campaign and the loss of a node, and presents its state on the live dashboard, accompanied by the final report. Stop shadows, the warm-restart snapshot cache, the Horde comparison, and deployment across physically separate machines are planned but can be trimmed if the schedule slips. Stretch goals include the what-if sandbox, a hot code upgrade performed on running shadows, TLS-encrypted Erlang distribution, and running one cluster node on an edge device such as a Raspberry Pi. High-fidelity simulation of traffic or passenger loads, real-time rail data, any form of control over TransLink systems, and public production hosting are out of scope.

### Team Organization and Workload

Each student owns one subsystem while contributing to code review, testing, and documentation across the whole project. The Ingestion Lead owns the feed sources, the poller and its failover, the request-budget governor, the circuit breaker, the observation router, and the vehicle shadow's domain logic. The shadow Runtime Lead owns the static reference data store, the `Digitalshadow` behaviour and its generic runtime, shadow activation and passivation, the baseline comparison, and the disruption shadow. The Distribution Lead owns clustering, route partitioning, cross-node lookup, ledger replication, and the route shadow. The Resilience Lead owns the recorder and replay corpus, the review of the supervision design, the chaos module, and the experiment harness. The Interface Lead owns the Phoenix application, the LiveView dashboard, the stop shadow, the repository and continuous integration, and the final demonstration video. A coordinator role rotates weekly, so that every member runs the Monday planning meeting, tracks the week's issues, and submits the Sunday deliverable at least once.

A typical week for each member consists of about one hour of meetings (a 45-minute planning meeting on Monday and a 15-minute midweek stand-up), about one hour of code review and documentation, and about six hours of focused development or experimentation. Within the 280-hour budget, Week 1 is front-loaded with learning, with roughly half of each member's time reserved for guided Elixir and OTP exercises, and Week 7 shifts most effort from development to evaluation and writing. Each Sunday submission is accompanied by a one-page status report that records progress against the plan, hours spent by each member, and any new risks.

### Development Practices and Tooling

The team will work in a single GitHub repository with a protected main branch, pull requests reviewed by at least one other member, and continuous integration that runs formatting checks, Credo, and the ExUnit suite, complemented by Dialyzer and by property-based tests written with StreamData for the decoding and normalization code. Livebook notebooks will serve as the team's laboratory for exploring the feeds, prototyping derived indicators, and running experiments, and they can attach directly to a running node to inspect live shadows. API keys will be supplied only through environment variables and never committed. Because Erlang distribution authenticates nodes with a shared cookie and does not encrypt traffic by default, the cluster will run only on an isolated local or container network.

### Risks and Mitigation

The largest risk is the learning curve, since team members may be new to Elixir, OTP, and functional programming; it is mitigated by structured exercises in Week 1, pair programming across subsystems, and an architecture in which most domain code consists of pure functions behind the `Digitalshadow` callbacks. The second risk is the data itself: the request quota, possible API outages, inconsistencies between real-time trip identifiers and the weekly static bundle, and fields the feeds do not populate. These are mitigated by the recorded corpus and replay source, which decouple development from the live API, by the Week 1 survey of what the feeds actually contain, and by keeping fidelity deliberately low. The third risk is distributed-systems friction, such as node naming, cookies, and port configuration, which is mitigated by establishing the cluster under Docker Compose on one machine before moving to several. The fourth risk is scope creep, which is controlled by the minimum viable outcome defined above, by the coordinator's weekly check against this plan, and by treating anything outside the weekly deliverables as a stretch goal.

### Expected Outcomes

At the end of seven weeks the team will deliver a running, reproducible, and documented low-fidelity shadow of TransLink's bus network; a `Digitalshadow` behaviour that is independent of the transit domain and could be reused for other city systems; measured results on fidelity, concurrency, distribution, fault tolerance, and abstraction; a final technical report; a recorded demonstration; and a final presentation. Beyond these artifacts, the project gives each student hands-on experience with OTP's design principles and an evidence-based answer to the question of how much of a digital shadow platform the BEAM already provides.
